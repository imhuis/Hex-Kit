# AGENTS.md
*版本：v1.1（2026-09-09）*

## 术语说明
- **最小充分方案**：指能完整通过**验收标准**中所有条目的最小改动集合。若存在多个等价方案，优先选择改动范围最小、扩散风险最低的。
- **规划“偏强”**：指允许使用较高的推理深度（如逐步推演边界、权衡替代方案），但建议不超过最大推理量的 80%。
- **执行“偏轻”**：指尽可能用直接、简单的代码实现，推理深度建议不超过最大量的 50%；若无法量化，则以“代码修改量”和“新增概念数”为参考。
- **不可逆操作**：指任何**无法通过 Git 回滚、简单撤销或已备份恢复**的操作，例如：删除远程数据、修改生产配置、移除用户文件、变更数据库 Schema 等。下列操作默认视为**可逆**，无需等待确认：
  - Git 回滚、还原、切分支（无论本地或远程）
  - 将文件移动到当前仓库内的备份目录（如 `./.backup/`）
  - 运行测试、查看 diff、生成只读分析报告、打印日志
- **外部依赖变更**：指修改 `package.json`、`requirements.txt`、`go.mod` 等清单，或调整环境变量、配置文件（如 `.env`、`config.yaml`），或升级/降级第三方库版本。此类变更默认需在计划中明确说明，并视为“需确认”的操作（除非用户另行授权）。

---

## 目的
用最小充分方案完成当前任务。
禁止过度工程化。
规划可以偏强，执行必须偏轻。
不能证明必要的设计，默认不做。
不能证明必要的测试，默认不加。

---

## 工作流
1. **先理解需求，再动手**。不要先改代码再猜意图。
2. **产出初步复述与范围**，必须包含：
   - 用户真正想要什么
   - 本次范围是什么
   - 明确不做的事
   - 怎样算完成（验收标准）
3. **等待用户确认**上述复述无误后，再进入规划阶段。若用户未回应，可追问一次，但不得擅自推进。
4. **规划阶段**允许较高推理，产出最小计划。计划必须写清：
   - 目标
   - 非目标
   - 验收标准
   - 不改动的范围
   - （若涉及）外部依赖或配置变更
5. **执行阶段**默认使用中低推理（或更轻量模型）。若执行过程中发现必须超出原定计划，立即停止，回到步骤 2，重新修订计划并再次等待用户确认。
6. **一个任务先单线做完**，再决定要不要拆分。不要默认并行拉起多个 Agent。
7. 只启用完成任务所必需的 skill。若需安装新 skill，必须在计划中论证必要性并获用户批准。

## 失败模式（需警惕）
1. 没有真正理解意图，只修了表面问题。
2. 本可以做一次干净的根因修复，却用历史补丁、兼容层、双轨实现、副本和分支把代码堆胖。
3. 为很少发生的情况过度设计，让日常维护成本变高。
4. 判断依据错了，推理再完整结论也是错的。
5. 本该直接读代码定位问题，却用检索或猜测替代阅读。
6. 把“补测试”当成继续加抽象、扩范围、显得完整的借口。

---

## 行动边界
- 动手前必须先**复述意图和验收标准**，并等待确认（见工作流第 2、3 步）。
- **不可逆操作**（定义见术语说明）必须等待用户回复**确认口令**后再执行。
  - 确认口令由用户指定。
  - 没有口令、口令错误、或其他回复，一律拒绝执行。
- 以上“不可逆”定义中的列举项默认可执行，无需等待口令。
- 发现自己正在做以下事情时，必须停下来改成更小方案：
  - 新增抽象、框架或配置层，但当前需求并不需要
  - 为了以后可能用到而提前设计
  - 为了满足约束而继续叠加更多约束
  - 同时改很多无关文件
  - 创造第二套实现来兼容旧逻辑
  - 借机补一套完整测试体系

## 测试
测试只服务于当前改动的验收。
测试不负责补齐历史覆盖率，不负责设计未来测试体系。

1. 优先跑与本次改动相关的现有测试。
2. 现有测试能证明改动正确，就不要新增测试。
3. 只有在下述情况才允许新增测试：
   - 这次改了行为，但现有测试覆盖不到该行为
   - 用户明确要求补测试
4. 新增测试数量**不超过本次改动带来的外部行为变化数**，且原则上不超过 2 个（1 个主路径 + 1 个关键失败路径）。若改动带来多个独立行为变化，可等比例增加，但需在计划中说明。
5. 若新增测试的代码量超过对应实现代码量的 2 倍，则需重新评估是否过度工程；若无法简化为更短测试，考虑缩小实现范围或将逻辑合并到已有测试中。
6. 禁止为了更完整而扩大测试范围。
7. 禁止借机补全无关模块的测试。
8. 禁止引入新的测试框架、测试工具或测试基础设施。
9. 禁止写大量快照、参数化矩阵或端到端套件。
10. 禁止为当前需求未要求的边界写测试。
11. 禁止先改测试再倒逼产品行为变复杂。
12. 禁止把测试变绿当成可以继续加抽象的理由。

**新增任何测试前，必须能回答：**
- 这个测试在验证哪个已被接受的需求？
- 去掉它，现有测试是否就无法发现这次回归？
- 它是不是比实现本身更复杂？

如果测试代码比实现代码更长或更绕，默认视为过度工程，应删测试或缩小实现。

## 模型分工
- 需求澄清和方案审查：使用较强推理（如可配置模型，则选高级别；若无法切换，则通过提示词要求“逐步推理”）。
- 写代码、改代码、跑测试：使用中低推理（或更轻量模型；若无法切换，则提示词中要求“直接输出最简实现”）。
- 发现执行模型开始叠架构、加兼容、扩范围、补大套测试时：立刻停下来，重写最小计划（回到工作流步骤 4）。

---

## 回退策略（当计划必须变更时）
若在执行过程中遇到以下情况，必须启动回退策略：
- 发现原定方案无法通过验收标准
- 发现需要修改未列入计划的文件或配置
- 发现依赖项或环境与预期不符

回退步骤：
1. **立即停止当前执行**，保留当前改动（可 commit 到临时分支）。
2. **回到工作流步骤 2**，重新复述新意图和范围。
3. 提交新计划，等待用户确认后再继续。

严禁在未通知用户的情况下擅自调整计划以绕过障碍。

---

## 完成前检查（最终核对清单）
- [ ] 已复述意图和验收标准，并获用户确认
- [ ] 方案是最小方案（不是最大方案），已标明非目标
- [ ] 优先读了相关代码，而不是靠检索拼结论
- [ ] 只改了完成任务所需的最小文件集，且 diff 小（无多余文件，无残留调试代码）
- [ ] 相关现有测试已跑过；若新增测试，只锁本次行为，且条数很少
- [ ] 测试没有引入新依赖或新目录结构
- [ ] 没有为了“看起来完整”而额外施工

若任何一项不满足，回退并重新调整。

---

## 总则
先确认意图，再用最小改动完成验收。
设计不能证明必要，默认不做。
测试不能证明必要，默认不加。
不可逆操作必问口令。
计划变更必走回退。
